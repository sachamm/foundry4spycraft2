# Spycraft 2.0 implementation audit — November 2026

Repository: `sachamm/foundry4spycraft2` · Base: v0.3.0 · Branch: `audit/rules-lifecycle-v14-20261112`.

## Workstream 1 — Rules correctness

- Cross-class skills now use **2 whole points per whole rank** at the level purchased. Odd cross-class allocations create warnings and cannot create half ranks.
- Each career level checks the skill-rank cap in force when points were spent, rather than only the present career cap.
- Skill-point minima are enforced (1 per level, quadrupled to 4 at first career level).
- Historical stage calculations reconstruct level-specific class ability bonuses, ability increases, acquisition-level feats, and bonuses to class-skill designations and skill points.
- A feat that no longer meets current prerequisites stays owned but no longer supplies its benefits. A fixed-point qualification calculation prevents a feat's own bonus from supplying its prerequisite.
- Unsupported prerequisite node types now fail qualification rather than silently succeeding.
- Current feat prerequisites remain relevant to feat usability, as required by the rulebook.
- Three existing reference fixtures remain under regression tests. **Caution:** existing fixtures include invalid rank allocations; those fixture totals are arithmetic baselines, not examples of legal character construction.

## Workstream 2 — Character lifecycle

- New expert-class entries capture entry-time prerequisite status, so later level-ups don't retroactively validate or invalidate the entry.
- New feat selections and grants record the earliest career level at which they were gained.
- Granted-feat synchronization preserves an explicit manual selection when removing automatically granted duplicates, avoids repeated grants, removes obsolete grants, and corrects legacy grant acquisition levels.
- Duplicate talents/specialties trigger warnings, including when imported without the browser.
- Armor equip is exclusive in the agent sheet; bad imports with multiple equipped suits warn.

## Workstream 3 — Combat and rolls

- The cap resolver reports the actual effective skill result, taking account of threats and Triumphs. Raw and effective results are also preserved in chat-message flags for downstream automation.
- Weapon attacks and damage rolls remain an **early implementation**: situational modifiers, damage-type effects, ammo use, multiple attack actions, and the wider tactical rules are not implemented comprehensively.
- Concurrent action-die spending from separate client sessions is **not transactionally safe**. A robust fix needs an authoritative cross-client update mechanism in Foundry; a local promise queue would not solve this.

## Workstream 4 — User interface

- A Node-based sheet harness tests actor and item form submission mappings and armor equip behavior.
- These are *not* browser-based Foundry 14 tests. The real client still needs validation: create/edit/level an agent, select options, roll dice, browse/add items, re-open after persistence, and test two simultaneous clients.

## Workstream 5 — Build and release

- Added validation workflow on pushes and pull requests: `npm ci`, `npm run build`, `npm test`, and syntax/manifest checks.
- Release workflow now builds packs and runs all tests before packaging.
- Generated compendium metadata uses the manifest's declared Foundry core version rather than hardcoded v13 metadata.
- Structural rules-data test checks class tables, skill and feat references, prerequisite types, bonus targets, origin grants, and equipment presence.
- The build succeeds for 30 classes, 314 feats, 68 origins, 394 weapons and 37 armor entries.

## Limitations requiring follow-up

1. **Foundry runtime:** No authorized/licensed Foundry v14 test installation is accessible from this environment. API docs and a mock harness do not replace an actual game client test. The PR should remain draft until a v14 playtest is done.
2. **Historical legacy characters:** Existing feats with no acquisition level default to the first level for historical reconstruction. There is no reliable way to infer past acquisition order from unrecorded data.
3. **Data semantics:** The structural integrity check does not prove all 314 feat summaries, class feature descriptions and 431 equipment stat blocks match printed Spycraft RAW. High-impact numeric entries merit an independent source-to-data audit.
4. **Combat scope:** The system's roll operations do not currently automate the entire Spycraft 2.0 combat system. Completing tactical mechanics is additional feature work, not a regression-only fix.
5. **Multi-client race:** Action-die deduction needs an authoritative concurrency design.
6. **Version and migration:** Before public release, bump the version, document the new persisted `acquiredAtLevel` and `expertEntry` fields, and test importing existing world data.

## Verification

- The tests run in GitHub Actions, including engine fixtures, pure unit tests, mocked actor/item sheet tests, granted-feat lifecycle tests, data-integrity checks, JavaScript syntax and JSON manifest validation.
- Static compatibility cross-check used the official Foundry VTT v14 API documentation.
- All changes were made on a branch and proposed through a draft PR; the default branch was not modified.
